# 知识迭代协议

本 skill 是**活的知识库**，不是一次性文档。目标：让每次踩坑都能被下一次写策略时
自动用上，且证据可追溯、结论可推翻但不可抹掉。

## 1. 单一事实源

- 规范路径：`skills/strategy-guardrails/`（项目根目录下，git 可见、可评审）。
- `.workbuddy/skills/strategy-guardrails` 是指向它的**符号链接**，用于让 WorkBuddy
  按项目级 skill 发现它。不要在软链下另写一份内容。
- `SKILL.md` 只放铁律与工作流；证据、schema、清单放 `references/`；
  确定性检查放 `scripts/`。同一条信息只写在一处。

## 2. 新增案例（每次实验 / 每个新坑）

1. 新建 `references/case-rNN.md`，NN 用项目里递增的实验编号（R29、R30…）。
2. 必须包含：
   - 待解释的现象与**至少 3 个**候选解释（包括被排除的）；
   - 实验设计：单变量、配置逐字段 diff、串行执行方式；
   - 完整结果表 + 关键差值，不只写支持结论的那几行；
   - 机制链（可画成文字流程），标明源码文件与行号；
   - **结论与边界**：明确写「不成立 / 不能外推」的部分；
   - 复现命令、run_id / config hash、输出文件路径、踩坑与修复。
3. 阴性结果同样入库。「关掉反馈后差距消失」和「改 allocator 后夏普变差」
   都属于必须保留的证据。

## 3. 修订规则

- 新证据与现有铁律冲突时，**不静默改写**：在 `case-*.md` 写明冲突，
  在 `SKILL.md` 对应条目加「例外 / 适用条件」，并在 `CHANGELOG.md` 标注
  「修订 Gx」或「推翻 Gx（原证据见 case-rNN）」。
- 每条铁律必须能指向至少一个案例；没有案例支撑的规则标注为「待验证」，
  不得写成硬约束。
- 阈值（50pp / 0.05 等）调整必须写明来自哪组数据、为什么旧阈值不合适。

## 4. 版本号

`CHANGELOG.md` 用语义版本，格式 `v0.MINOR.PATCH`：

| 变更 | 版本 |
|---|---|
| 追加案例、补充证据、修文档措辞 | patch |
| 新增铁律 / 新增脚本 / 新增检查项 | minor |
| 推翻既有铁律、重构工作流 | major（0.x 阶段用 minor，1.0 后按语义） |

每次改动都要在 `CHANGELOG.md` 追加一行，注明日期、版本、改动、证据来源。

## 5. 回顾节奏

- 每积累 5 个案例，做一次回顾：合并重复规则、把已稳定的知识下沉到脚本、
  把已被推翻的结论标记为历史而非删除。
- 每次回顾后重新跑 `scripts/check_strategy.py` 与
  `scripts/check_scale_invariance.py` 的自检，确认脚本仍与引擎输出结构兼容。
- 引擎 schema 变更（`src/protocol.py` / `core/calculation.py`）时，
  优先检查 `engine-contract.md` 与两个脚本是否需要同步。
